**推理闸：**问题是格式已可解析但 Android 仍无法按资源选择和恢复，且上游模型运行时与本仓第一人称/头饰深度分叉。资源绑定的 owner 是 `native/modules/custom_model`；Android UI 和安装器只能消费该合同。最简单的“直接移植整个上游 module.cpp”会覆盖本仓行为并引入未验设备链路，因此按绑定、接收、作业三段推进。阶段 1 的完成不代表 BEM 1.4 产品支持；失败时继续拒绝，不能靠静默降级把 1.4 当 1.3 加载。

## 阶段 3 热切换依赖审计（2026-10-09）

本地 `XposedEntry` 只在游戏启动时准备已安装包，`ResourceConfigurationChanged` 只更新独立 LOD；运行中模型热切换目前缺失。移植次序必须是：① BEM 内容与不可变安装代际身份；② 验证候选注册表后原子切换，并使旧 `OwnedCharacterAdapter` 在已完成绑定期间继续存活；③ 保存原始 Mesh、材质、骨骼和阴影代理，定义禁用恢复；④ 场景已克隆实例的有界发现、重绑与失败保留；⑤ Android 单 worker 更新器及配置投递。只拷贝上游 Java 更新器会留下悬空 adapter 和旧外观实例。

候选注册表解析现改为成功后才替换输出；畸形配置不会清空已有资源和 adapter，原生夹具已覆盖。此项仅为热切换前置，尚未建立旧 adapter 生命周期、场景重绑和运行中配置投递。

已发布资源记录现显式持有对应 `OwnedCharacterAdapter` 的共享所有权；注册表换代后，仍被旧资源记录引用的 adapter 可以继续存活。原生夹具覆盖注册表成功换代后的旧 adapter 存活，Android ARM64 调试构建通过。仍须设计旧资源恢复与记录释放条件，不能仅凭引用存活启用热切换。

运行时现拒绝在同一 Unity 资源实例上直接叠加另一配置代际的替换。初始审计发现 `CompletedBinding` 只保存新 Mesh、材质及可见状态，原始状态仅在事务中的 `PreparedBinding` 暂存；该问题已促成本轮弱引用快照接入。要开放旧实例恢复和重绑，仍须保证原网格存活并验证恢复。拒绝保护本身不提供热切换能力。

已发布记录现捕获原始 Mesh、逐槽材质、骨骼数组和 Android 阴影代理的弱引用及可见状态，作为后续恢复的身份依据。弱引用本身无法阻止 Unity 卸载原网格，因此另接入下述有条件的原网格 pin；完整恢复与释放规则仍未闭合。

原网格 pin 已按上游合同定向接入：仅 `hot_switch=true` 且新网格替换原网格时保留强引用，并要求 Unity `DontUnloadUnusedAsset` 标志可设置和读回；原阴影网格被替换时同样处理。同一原网格按实例 ID 共享 pin，最后持有者释放时清除本轮添加的标志。若 Unity 合同不可用，准备阶段拒绝发布，保留原资源。Android ARM64 编译通过；关闭模块时的 Unity 线程释放、原材质/骨骼恢复和设备内存仍待验证，不能因此启用热切换更新器。

审计发现安装端尚未发布热切换配置，而模块的 `hot_switch=true` 会提前启用 pin，关闭模块时又没有可确认的 Unity 线程清理。现明确拒绝该未完成配置并记录原因，避免设置被误认为已生效或留下防卸载标志。待原网格 pin 的关闭清理与恢复事务闭合后，再由 Android 配置入口正式发布并解除拒绝。
